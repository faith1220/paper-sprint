# 证据规则和可执行范围

## 四类材料分开

| 材料 | 能支持什么 | 不能支持什么 |
| --- | --- | --- |
| 论文原文与机制卡 | 技术来源、原方法条件和作者报告 | 本项目已复现或已取得相同分数 |
| synthetic 演示 | CLI、协议和登记流程可运行 | 科学效果、真实模型性能、投稿结论 |
| 开发集结果 | 候选、阈值、参数与成本选择；标明开发集的消融观察和机制讨论 | 独立保留集上的泛化结论 |
| 固定选择后的真实测试结果 | 在已声明条件下的方法比较 | 未测试场景、普遍最优或必然录用 |

论文写作的基本单位是“论断—来源／运行—范围—边界”。平均分提升、成本降低、机制互补、鲁棒性提高是不同论断，应分别提供对应证据。完整组合优于基线不足以证明每个模块都有效；模块贡献需单模块与组合消融。

## 记录规则

保存所有运行，包括成功、崩溃、OOM、无提升和超预算。失败没有有效指标时用 null，不用零分代替缺失。重试使用新 run ID，保留原因与旧记录；禁止只留下最后一个成功版本。实际成本超过预算时先入账，再停止安排后续运行。

所有 arm 遵循冻结的配置比较原则。代码版本、数据划分、seed、评价流程、调参预算、原始日志和配置需可追溯。比较不同实验条件时应明确限制，不把额外训练成本隐藏为模块贡献。

最小有意义提升在实验前声明。负结果不自动意味着项目失败：若成本、特定条件或机制分析仍有可信发现，可据此缩小目标；若最小论断无法得到支持，应停止或简化，并保留已完成材料。

## CLI 能检查的事情

结构、必填字段、允许的模块和 arm、数据清单互斥、协议 hash、结果身份、seed 和 split、文件 hash、开发选择与测试解锁、预算累计、论断指向的已登记运行。严格校验失败应修复实质缺口，不能只用占位文本填满字段。

这些是机械检查。程序无法确认检索是否充分、论文是否读懂、许可证判断是否正确、日志是否来自真实训练、训练脚本是否偷看测试集，或论断是否得到科学支持。它不解析原始日志核对所填指标，也不核实代码版本指向的 commit。本地文件可由用户编辑，hash 不是第三方不可篡改证据。

## 稿件状态

无真实运行：计划或待填稿。只有开发结果：方法与开发观察可以写，但最终效果仍待填。已有真实最终测试且论断映射完整：可以进入证据驱动的成稿与人工复核。`EVIDENCE_READY` 表示登记材料满足当前程序条件，不意味着论文“已经能中一区／二区”。

如结论依赖更多数据集、跨域测试、统计检验或机制解释，应在主张中收窄范围或补做相应证据；不为追求顶刊式排场自动增加不可负担的验证。
