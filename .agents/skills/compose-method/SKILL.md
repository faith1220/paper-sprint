# 把机制组成可验证的方法

读取 brief、已有机制卡与 [总控](../../../program.md) 的阶段 2。默认一个强基线加两项机制，最多三项，核心技术来自 2～3 篇论文。不因为创新增量较小而否决已知互补、轻量适配或应用验证路线。

使用 [候选模板](../../../templates/composition-candidate.md) 写至多三个候选。每个候选须包含：问题中的具体失败模式；各机制的来源；模块之间的数据流和接口；可证伪的互补假设；与最近邻的差异；成本估计；最可能失败的假设；一个去掉机制后的简化版本。

先排除接口无法兼容、必要监督不可获得、来源有误或确实无法追溯、超出预算的候选。只是全文或材料暂缺时，保留为条件候选并列出补证任务，在协议冻结前核实。对剩余方案按问题契合度、机制互补、实现成本和证据可获得性排序。已有近邻并非必然终止：若仍有可说明的新场景或适配，可缩小贡献表述后继续。

收敛到一个主方案，保留未选候选及原因。只用开发集进行 pilot 和选型；不要从测试分数反推故事。第三项机制需说明它解决的残余问题，以及为何两项机制已不够。

输出选定候选、基线与模块对应、实验优先级、失败后的简化路线。将“预计互补”标为假设，交给实验阶段验证，不先生成结果性摘要。
